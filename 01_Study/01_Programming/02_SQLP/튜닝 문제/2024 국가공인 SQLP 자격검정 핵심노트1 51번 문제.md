### 테이블 구성 및 데이터
- 주문상품은 비파티션 테이블
- 한 달 주문상품 = 100만 건
- 주문상품의 보관 기간 = 10년
- 주문상품 총 건수 = 총 1억 2천만 건(=100만 * 120개월)
- 할인유형코드 조건을 만족하는 데이터 비중 = 10%
- 등록된 상품 = 50만 개 / 속성 = 500개
- 대부분 상품을 한 달에 한 개 이상 주문

### 인덱스 구성
- 상품_pk : 상품코드
- 주문상품_pk : 고객번호 + 상품코드 + 주문일시
- 주문상품_x1 : 주문일시 + 할인유형코드

### 튜닝 전 코드
```
select p.상품코드, min(p.상품명) 상품명, min(p.등록일시) 등록일시,
	 min(p.상품가격) 상품가격, min(p.공급자ID) 공급자ID,
	 sum(o.주문수량) 총주문수량, sum(o.주문금액) 총주문금액
from 주문상품 o, 상품 p
where o.주문일시 >= add_months(sysdate, -1)
  and o.할인유형코드 = 'K890'
  and p.상품코드 = o.상품코드
group by p.상품코드
order by 등록일시 desc
```

### 기존 쿼리 실행계획 설명

1. 주문상품 테이블이 파티션 프루닝이 적용되고 인덱스 주문상품_x1을 이용하여 스캔함. (cost=104k)
2. 상품 테이블은 상품_pk로 unique 인덱스 스캔함
3. 주문상품 테이블과 상품 테이블은 nl조인을 실행함.(cost=204k)
4. 상품 테이블에서 상품코드별로 그룹핑이 일어남.
5. 정렬이 일어남.

### 기존 실행 계획에 대한 나의 생각
문제에서 '결과집합을 일부(보통 상위 100개)만 출력하고 멈추는 애플리케이션 환경' 이라고 한다. 이는 부분범위처리를 하라는 이야기인데 인덱스에 order by 컬럼을 추가하면 좋다.
`상품_x1 (상품코드+등록일시)` 를 추가한다.
상품 테이블의 경우 50만 건에다가 속성이 500개인 매우 큰 테이블이지만 등록일시를 기준으로 상위 100개가 고정되어 있다면 nl조인을 할 만 하다.

그러므로 상품 테이블을 드라이빙 테이블로 잡아줄 것이다.

주문상품 테이블의 경우 1억 2천만 건에서 주문일시 조건으로 100만건으로 줄고, K890 조건을 만족해서 20만건으로 줄어든다. `대부분 상품을 한 달에 한 개 이상 주문` 한다고 하는 조건은 데이터를 축소시켜주는 조건은 아니고 ndv가 2만개라는 말이다. 
일단 주문상품의 선택도를 계산해보면 (10 / 100 = 10%) 10%로 계산된다. 인덱스를 타게 하는 것이 더 나을 수 있다. 기존의 인덱스로는 안된다. 조건컬럼 중 등치조건의 컬럼이 선두 컬럼인 인덱스가 없기 때문이다. 그래서 
`주문상품_x2 (상품코드+할인유형코드+주문일시)` 를 만들어 주고 시작한다.


### 개선 튜닝1
```
select /*+ leading(p o) use_nl(o) index(o 주문상품_x2) */
	p.상품코드, p.상품명, p.등록일시, p.상품가격, p.공급자ID,
	sum(주문수량) 총주문수량, sum(주문금액) 총주문금액
from (
	select *
	from (
		select /*+ index(p1 상품_x1) */
			상품코드, 상품명, 등록일시, 상품가격, 공급자ID
		from 상품 p1
		group by p1.상품코드
		order by 등록일시 desc
	)
	where rownum <= 100
) p, 주문상품 o
where 1=1
and p.상품코드 = o.상품코드
and a.주문일시 >= add_months(sysdate, -1)
and a.할인유형코드 = 'K890'
group by p.상품코드
order by 등록일시 DESC
```

### 보완할 점1
1. `상품_x1(상품코드+등록일시)` 로는 ORDER BY 등록일시를 순서대로 읽기 어렵다. 상품코드가 선두컬럼인데 등치 조건이 없으므로 전체 인덱스를 읽게 되면서 등록일시 순서가 보장되지 않는다. 따라서 `상품_x1(등록일시 DESC, 상품코드)` 또는 `상품_x1(등록일시, 상품코드)` 로 해서 `index_desc(p 상품_x1)` 을 지정하는 것이 좋다.
2. 상품 100개를 조인 전에 자르면 결과가 달라질 수 있다. 문제에서 원하는 결과는 'K890 주문이 존재하는 상품 중 일부만 출력하고 멈출 수 있는 부분범위처리'이다. 꼭 100개가 나와야 하는 것이 아님을 명심한다. 따라서 내가 튜닝한 쿼리는 해당 문제의 의도를 벗어난다.
3. 인라인 뷰의 group by 문법 오류가 존재한다. group by하면서 다른 일반 컬럼을 조회할 수 없다. 

### 최종 개선 쿼리
```
select /*+ leading(p o) use_nl(o) index_desc(p 상품_x1) */
	p.상품코드, p.상품명, p.등록일시, p.상품가격, p.공급자ID, o.총주문수량, o.총주문금액
from 상품 p, (
	select /*+ no_merge push_pred index(a 주문상품_x2) */ 
		상품코드, sum(주문수량) 총주문수량, sum(주문금액) 총주문금액
	from 주문상품 a
	where 1=1
	  and a.주문일시 >= add_months(sysdate, -1)
	  and a.할인유형코드 = 'K890'
	group by 상품코드
) o
where 1=1
  and p.상품코드 = o.상품코드
order by 등록일시 DESC;

```

### 최종 개선 쿼리 예상 실행 계획
```
SELECT STATEMENT
    └─ NESTED LOOPS
        ├─ TABLE ACCESS BY INDEX ROWID 상품
        │    └─ INDEX FULL SCAN DESC 상품_X1
        └─ VIEW PUSHED PREDICATE
             └─ SORT GROUP BY
                  └─ TABLE ACCESS BY INDEX ROWID 주문상품
                       └─ INDEX RANGE SCAN 주문상품_X2
```


> Q1. 실행계획에서 인라인 뷰는 메인쿼리보다 하단에 위치하고 스칼라 서브쿼리는 메인쿼리보다 상단에 위치하는 것이 맞아?
> 
> A1. 인라인 뷰는 아래, 스칼라 서브쿼리는 위에 보이는 것은 맞지만, 실행계획의 위/아래만으로 **먼저 실행된다**
> 고 판단하면 절대 안된다. 상관 스칼라 서브쿼리는 부모 쿼리의 행을 받아 반복 평가될 수 있기 때문에 개념적으로 부모 쿼리가 처리하는 행마다 평가된다고 설명된다.
> 
> 인라인 뷰는 보통 메인 쿼리의 자식 연산으로 나타난다.
> ```
> NESTED LOOPS
	├─ TABLE ACCESS 상품
	└─ VIEW
	   └─ SORT GROUP BY
	      └─ TABLE ACCESS 주문상품
> ```
> 여기서 `VIEW`가 아래에 있다고 해서 반드시 메인 쿼리보다 먼저 전체 실행되는 것은 아니다.
> 특히 `VIEW PUSHED PREDICATE` 라면 아래처럼 메인 쿼리의 드라이빙 행마다 반복 실행될 수 있다.
> ```
> 상품 1건 읽기 -> 그 상품코드를 VIEW 안으로 전달 -> VIEW 실행 -> 다음 상품 읽기 -> VIEW 다시 실행
> ```
>
