### 테이블 구성 및 데이터
- 주문상품은 월 단위 파티션 테이블(주문일시 기준)
- 한 달 주문상품 = 100만 건
- 주문상품의 보관 기간 = 10년
- 주문상품 총 건수 = 총 1억 2천만 건(=100만 * 120개월)
- 할인유형코드 조건을 만족하는 데이터 비중 = 10%
- 등록된 상품 = 50만 개 / 속성 = 500개
- **할인유형코드 = 'K890' 조건으로 판매되는 상품은 5,000개**

### 인덱스 구성
- 상품_pk : 상품코드
- 주문상품_pk : 고객번호 + 상품코드 + 주문일시
- 주문상품_x1 : 주문일시 + 할인유형코드

### 튜닝 전 코드
```
select p.상품코드, min(p.상품명) 상품명, min(p.등록일시) 등록일시,
	 min(p.상품가격) 상품가격, min(p.공급자ID) 공급자ID,
	 sum(o.주문수량) 총주문수량, sum(o.주문금액) 총주문금액
from 주문상품 o, 상품 p
where o.주문일시 >= add_months(sysdate, -1)
  and o.할인유형코드 = 'K890'
  and p.상품코드 = o.상품코드
group by p.상품코드
order by 등록일시 desc
```

### 기존 쿼리 실행계획 설명

1. 주문상품 테이블이 파티션 프루닝이 적용되고 인덱스 주문상품_x1을 이용하여 스캔함. (cost=104k)
2. 상품 테이블은 상품_pk로 unique 인덱스 스캔함
3. 주문상품 테이블과 상품 테이블은 nl조인을 실행함.(cost=204k)
4. 상품 테이블에서 상품코드별로 그룹핑이 일어남.
5. 정렬이 일어남.

### 기존 실행 계획에 대한 나의 생각
문제에서 '결과집합을 일부만 출력하고 멈추는 애플리케이션 환경' 이라고 한다. 이는 부분범위처리를 하라는 이야기인데 인덱스에 order by 컬럼을 추가하면 좋다. `상품_x1(등록일시)` 인덱스를 추가한다.

주문상품의 경우 총 데이터가 1억 2천만 건인데 월 단위 파티션 테이블이다. 한달 데이터는 100만건, 할인유형코드 조건을 만족하면 10만건이다. 선택도(10%)

상품 테이블은 총 건수가 50만개에 속성도 500개지만 할인유형코드에 만족하는 상품은 5,000개밖에 안하므로 선택도는 (5000 / 500000 = 1%) 1%이다. 이러면 fts보다 인덱스를 타는 것이 좋을 수도 있다.
하지만 할인유형코드 조건을 타려면 주문상품 테이블을 우선 접근하고 난 후 조인해야 하는데, 주문상품을 드라이빙 테이블로 잡기에는 10만건은 너무 많은 듯한 느낌이다.

결국 상품테이블을 드라이빙 테이블로 선택하면 할인유형코드에 만족하는 상품 5000개를 무시하고 50만개에서 등록일시 인덱스로 정렬 생략하는 것이고, 주문상품 테이블을 드라이빙 테이블로 선택하면 할인유형코드에 만족하는 상품 5000개를 선택할 수 있지만 주문상품 테이블에서 축소한 데이터가 10만건에 해당한다. nl 조인을 하기에는 많은 데이터이다.

주문상품 테이블을 인라인 뷰로 하게 되면 총 건수는 5000 건이 된다.


### 개선 튜닝1
```
select /*+ leading(p o) use_nl(o) index_desc(p 상품_x1) */
	p.상품코드, p.상품명, p.등록일시, p.상품가격, p.공급자ID,
	총주문수량, 총주문금액
from (
	select /*+ no_merge push_pred index(a 주문상품_x2) */
		상품코드, sum(주문수량) 총주문수량, sum(주문금액) 총주문금액
	from 주문상품 a
	where 1=1
	  and a.주문일시 >= add_months(sysdate, -1)
	  and a.할인유형코드 = 'K890'
	group by 상품코드
) o, 상품 p
where 1=1
and p.상품코드 = o.상품코드
order by 등록일시 DESC
```

### 보완할 점1
1. 위 쿼리는 **정렬을 없대고 중간에 멈출 수 있는 구조**는 만들었지만, **조건을 만족하는 상품이 드물어서 첫 결과 묶음을 얻기 전까지는 발생하는 반복 탐색 비용이 크다.**
   
   상품을 등록일시 역순으로 읽으면 흐름은 다음과 같다.
   ```
   최신 상품 1건 -> 주문상품 인덱스 조회 -> K890 주문 없음 -> 버림
   다음 상품 1건 -> 주문상품 인덱스 조회 -> K890 주문 없음 -> 버림
   ```
   K890 으로 판매된 상품이 5,000개라면 전체 50만 상품 중 비율은 ' (5000 /. 00000 = 1%) 1%' 균등 분포를 가정하면 결과 1건을 찾기 위해 평균적으로 상품 약 100개를 확인해야 하고, 결과 100건을 채우려면 약 10,000개 상품을 읽어야 한다. 특히 nl 조인에서는 후행 집합인 주문상품 인덱스 탐색이 Starts  = 10,000 이 될 수 있다.
   
   따라서 **형식적으로 부분범위 처리지만 '많은 실패 조인을 거친 후에야 결과가 조금씩 나오는 부분범위 처리'**가 된다.
   
   반대로 주문상품부터 처리하면 아래와 같은 흐름이 된다.
   ```
   최근 한 달 파티션 읽기
   -> K890 10만 건
   -> 상품별 group by
   -> 약 5000개 상품 생성
   -> 상품 조인
   -> 등록일시 정렬
   -> 결과 출력
   ```
   이 방식은 상품 495000건에 대한 실패 조인은 피하지만, `group by`와 `order by` 가 전체 처리를 막는 블로킹 연산이다. 따라서 첫 행이 나오기 전에 다음과 같은 흐름이 필요하다.
   ```
   주문상품 조회 완료
   -> 집계 완료
   -> 상품 조인 완료
   -> 정렬 완료
   ```
   이 문제는 데이터 분포의 중요도와 딜레마의 케이스이다.
   
   
2. 1%라는 값은 일반적인 상품 테이블 검색 조건의 인덱스 선택도가 아니지만 상품을 드라이빙으로 NL 조인할 때의 조인 성공률로는 매우 중요한 수치이다.
   따라서 이 수치로 판단해야 하는 것은 '상품을 최신순으로 읽으며 주문상품을 반복 탐색할 때 얼마나 자주 성공하는가?' 이다.
	   

### 해설지의 쿼리
```
--인덱스 추가
상품_x1 (등록일시 + 상품코드)

-- 1안
select /*+ leading(c p) use_nl(p) */
	p.상품코드, p.상품명, c.등록일시, p.상품가격, p.공급자ID, c.총주문수량, c.총주문금액
from (
	select /*+ leading(b) use_hash(a) full(a) index_ffs(b) */ 
		a.상품코드, sum(주문수량) 총주문수량, sum(주문금액) 총주문금액,
		min(b.등록일시) 등록일시
	from 주문상품 a, 상품 b
	where 1=1
	  and a.주문일시 >= add_months(sysdate, -1)
	  and a.할인유형코드 = 'K890'
	  and a.상품코드 = b.상품코드
	group by 상품코드
	order by 등록일시 DESC
) c, 상품 p
where p.상품코드 = c.상품코드;

-- 2안
select /*+ leading(c p) use_nl(p) */
	p.상품코드, p.상품명, p.등록일시, p.상품가격, p.공급자ID, c.총주문수량, c.총주문금액
from (
	select /*+ leading(b) use_hash(a) full(a) index_ffs(b) */ 
		b.상품코드, min(b.rowid) ROWID, min(b.등록일시) 등록일시, sum(주문수량) 총주문수량, sum(주문금액) 총주문금액
	from 주문상품 a, 상품 b
	where 1=1
	  and a.주문일시 >= add_months(sysdate, -1)
	  and a.할인유형코드 = 'K890'
	  and a.상품코드 = b.상품코드
	group by 상품코드
	order by 등록일시 DESC
) c, 상품 p
where p.ROWID = c.ROWID;
```

### 해설지의 설명
해설은 다음과 같은 방식으로 접근하려고 하는 것이다.
```
상품 인덱스 INDEX FAST FULL SCAN -> 해시 테이블 생성
최근 1개월 주문상품 파티션 FULL SCAN -> K890 조건 필터링 -> Hash Probe
상품코드별 주문 집계 -> 상품 등록일시 기준 정렬
정렬된 결과를 상품 테이블과 NL 조인 -> 필요한 상세 컬럼 조회
```
내가 하려고 하는 접근방법을 포기하고 주문상품을 한 번에 읽어서 5,000개 상품을 먼저 확정하는 접근방식이다.
내가 full 힌트를 사용하게 되면 파티션 프루닝을 무효화하고 전체 건수를 스캔하는 것으로 잘못 알고 있는데, 파티션 프루닝은 적용된 채로 테이블 full scan을 진행하게 된다. 따라서 1억 2천만건이 아닌 100만건의 데이터를 full scan 하는 것으로 생각하면 된다.

인라인 뷰에서는 Hash join + group by + order by 를 마쳐야 첫 행이 나오므로 부분범위 처리할 수 없다. 하지만 최근 파티션을 한 번 순차 스캔하는 안정적인 전체범위 처리가 낫다고 해설자는 생각한 것이다. 특히 주문상품 테이블 전체 1억 2천만 건이 아니라 최근 한 달 파티션 100만 건만 읽는다면, 이 판단은 충분히 현실적이다.



> Q1. 50만 건의 데이터를 해시 맵에 올리는 것은 큰 데이터인가?
> 
> A1. 오히려 Hash Join 입장에서는 50만 건은 작은 편이다. 실무에서는 수백만, 수천만 건도 자주하기 때문이다.
> 

 >Q2. 파티션 테이블에서 파티션 프루닝 조건만 되면 fts 힌트를 넣어도 옵티마이저가 자동으로 해당 파티션을 찾아 가는가?
> 
>A2. 파티션 테이블의 중요한 특징으로 Full 힌트를 주더라도 파티션 프루닝 조건이 성립하면 옵티마이저는 해당 파티션만 full scan 한다. 즉, full은 테이블 전체를 읽는 것이 아닌 '선택된 액세스 대상에 대해 full scan을 사용하라' 는 의미이다.
