### 테이블 구성 및 데이터
- 주문상품은 월 단위 파티션 테이블 (주문일시 기준)
- 한 달 주문상품 = 100만 건
- 주문상품의 보관 기간 = 10년
- 주문상품 총 건수 = 총 1억 2천만 건(=100만 * 120개월)
- 할인유형코드 조건을 만족하는 데이터 비중 = 20%
- 등록된 상품 = 2만 개
- 할인유형코드 = K890 조건으로 판매되는 상품은 100여 개

### 인덱스 구성
- 상품_pk : 상품코드
- 주문상품_pk : 고객번호 + 상품코드 + 주문일시
- 주문상품_x1 : 주문일시 + 할인유형코드

### 튜닝 전 코드
```
select p.상품코드, min(p.상품명) 상품명, min(p.상품가격) 상품가격, sum(o.주문수량) 총주문수량
	, sum(o.주문금액) 총주문금액
from 주문상품 o, 상품 p
where o.주문일시 >= add_months(sysdate, -1)
  and o.할인유형코드 = 'K890'
  and p.상품코드 = o.상품코드
group by p.상품코드
order by 총주문금액 desc, 상품코드
```

### 기존 쿼리 실행계획 설명
```
	1. 주문상품 테이블이 파티션 프루닝이 적용되고 인덱스 주문상품_x1을 이용하여 스캔함. (cost=104k)
	2. 상품 테이블은 상품_pk로 unique 인덱스 스캔함
	3. 주문상품 테이블과 상품 테이블은 nl조인을 실행함.(cost=204k)
	4. 상품 테이블에서 상품코드별로 그룹핑이 일어남.
	5. 정렬이 일어남.
```

### 기존 실행 계획에 대한 나의 생각
이 실행계획은 nl조인으로 처리했으나 드라이빙 테이블이 주문상품 테이블인 것으로 보여진다. `할인유형코드='K890'` 을 만족하는 상품은 100 개이므로 **드라이빙 테이블은 상품 테이블이 되는 것이 더 효율적**이다.
해시조인도 괜찮지만 상품 스캔 데이터를 100개로 줄인다면 nl조인도 나쁘지 않다.

상품 데이터 2만 개 중 100 개면 선택도가 많이 줄어드므로 인덱스를 타는 것이 full 스캔보다 좋다.
그러므로 주문상품을 우선 건수를 줄이고 나서 **상품 테이블을 full 스캔하는 것이 좋을 것** 같다.

주문상품 테이블은 1억 2천만 건이지만 조건들을 모두 만족하는 건수는 20만건이다. 선택도( 20 / 12000 = 1% 미만) 이므로 인덱스 스캔하는 것이 더 좋다. **하지만** 주문상품 테이블은 **주문일시를 기준으로 월 파티션**이 되어 있다. 그리고 조건 컬럼은 `주문일시`이다. 그러면 굳이 인덱스를 타지 않고 full 스캔을 해도 괜찮다. 왜냐하면 데이터 스캔은  파티션 프루닝 조건이 적용하고 파티션 세그먼트로 진입한 후에 진행하기 때문이다.

### 개선 튜닝1
```
select /*+ leading(o) use_nl(p) index(p 상품_pk) */
	p.상품코드, p.상품명, p.상품가격, 총주문수량
	, 총주문금액
from 상품 p, (
	select /*+ no_merge push_pred full(a) */ 
		상품코드, sum(주문수량) 총주문수량, sum(주문금액) 총주문금액
	from 주문상품 a
	where a.주문일시 >= add_months(sysdate, -1)
	  and a.할인유형코드 = 'K890'	
) o
where p.상품코드 = o.상품코드
group by a.상품코드
order by 총주문금액 desc, 상품코드
```

### 보완할 점1
1. **인라인 뷰에 집계함수가 있지만 group by 절이 빠져있다.**
2. 내가 원하는 전략은 '주문상품을 한 번 스캔하여 상품코드별로 집계하고, 그 결과 약 100건을 바깥으로 넘기려는 전략' 이므로 외부 조인 조건을 인라인 뷰 안으로 밀어넣는 **push_pred 힌트는 부적합**하다.
3. 주문상품 테이블에서 선택도 계산의 경우 전체 테이블 기준으로는 1% 미만이지만, 이 쿼리에서는 `주문일시` **기준 월 파티션이므로 접근 방식 판단에서는 파티션 프루닝 후의 선택도가 더 중요하다.**

	> 최근 한 달 데이터 약 100 만건 -> K890 약 20 만건 = 20%

	선택도가 20%이면 인덱스 스캔하는 것보다 full 스캔이 더 합리적이라는 결과가 나온다.
	또한 `주문상품_x1` 컬럼 구성을 보면 `주문일시`가 선두 컬럼으로 지정되어 있다. `할인유형코드` 등치 조건이 인덱스 스캔 범위를 효과적으로 좁혀주는데 `주문일시`가 선두 컬럼으로 지정됨에 따라 최근 기간의 인덱스 영역을 비교적 넓게 읽고, 그 중 `K890` 판별한 뒤 약 20만건을 rowid로 방문하게 된다. `주문일시`의 조건 `add_months(sysdate, -1)` 은 월 시작일이 아니라 **현재 시점의 한 달 전부터이므로, 실제로는 보통 두 개의 월 파티션 일부가 선택될 수 있다.**

> Q1. 파티션 프루닝이 적용되면서 인덱스 스캔도 가능한가? 만약 `주문상품_xl`이 `할인유형코드+주문일시`라면 인덱스 스캔이 더 효과적일 수도 있었을까?
> 
> A1. 만약 `주문상품_x1`이 `할인유형코드+주문일시` 라면 full 스캔 보다 인덱스가 훨씬 경쟁력이 있었을 가능성이 높다. 
> 
> '파티션 프루닝이 되면 인덱스는 필요 없다' 라고 생각하는데 그건 아니다. 순서는 다음과 같다.
> 1. 파티션 프루닝
> 2. 인덱스 탐색
> 3. ROWID 랜덤 엑세스
> 
> `할인유형코드`가 인덱스 선두 컬럼이 된다 한들 최종적으로는 20만 건을 가져와야 한다. 그러면
> 	INDEX RANGE SCAN -> 20만 ROWID -> TABLE ACCESS BY ROWID
> 가 된다. 즉, 랜덤 엑세스가 20만번 발생한다.
> 하지만 full 스캔은
> 	7월 파티션 -> Sequential Read -> 20만건 추출
> 작업 하므로 20만 건을 모두 가져오는 순간에는 full 스캔이 여전히 이길 수도 있다.

>Q2. 상품 테이블에 대한 조건절이 조인 조건밖에 없어서 push_pred 힌트가 부적합한 걸로 이해해도 될까? 만약에 상품 데이터에 조건이 더 있었다면  push_pred 힌트가 효과적이 될 수 있을까?
>
>A2. 핵심은 상품 테이블에 추가 조건이 없어서 push_pred 를 쓰면 안되는 것이 아니라, 밀어 넣을 조인 조건의 값이 몇 개이며, 그 값으로 인라인 뷰 내부의 주문상품 접근량을 실제로 줄일 수 있느냐이다.
>
>만약 상품 테이블에 아래 조건이 있고 이 조건으로 상품이 2만 건 -> 10건으로 줄어든다고 가정한다면,
>```
>where p.상품분류코드 = 'A01'
>and p.판매상태 = 'Y'
>and p.상품코드 = o.상품코드
>```
>
>이 때 상품 10 건을 먼저 구한 뒤, 각 상품코드를 주문상품 인라인 뷰에 밀어 넣으면 주문상품 전체를 일괄 집계하지 않고 필요한 상품만 조회할 수 있다. 이런 경우에는 push_pred 가 효과적일 수 있다. 단, 주문상품 인덱스에 상품코드 컬럼도 포함되어 야 한다. 외부 상품코드를 내부로 밀어 넣어도 주문상품에서 상품코드로 효율적으로 접근할 방법이 없다면 이점이 적다. 만약 인덱스가 `상품코드+할인유형코드+주문일시` 또는  `상품코드+주문일시` 일 경우, 외부에서 들어온 상품코드로 인덱스에 바로 진입할 수 있다. 반면 인덱스가 `주문일시+할인유형코드`일 경우, 상품코드는 인덱스에 없으므로 주문상품 접근 범위를 줄이는 데 기여하지 못한다.
>
>따라서 인라인 뷰에서 full 스캔을 한다면 push_pred 힌트는 생각보다 효과가 없다.
