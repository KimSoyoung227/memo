### 테이블 구성 및 데이터
- 주문상품은 비파티션 테이블
- 한 달 주문상품 = 100만 건
- 주문상품의 보관 기간 = 10년
- 주문상품 총 건수 = 총 1억 2천만 건(=100만 * 120개월)
- 할인유형코드 조건을 만족하는 데이터 비중 = 20%
- 등록된 상품 = 2만 개
- 2만 개 상품을 고르게 주문

### 인덱스 구성
- 상품_pk : 상품코드
- 주문상품_pk : 고객번호 + 상품코드 + 주문일시
- 주문상품_x1 : 주문일시 + 할인유형코드

### 튜닝 전 코드
```
select p.상품코드, min(p.상품명) 상품명, min(p.상품가격) 상품가격, sum(o.주문수량) 총주문수량
	, sum(o.주문금액) 총주문금액
from 주문상품 o, 상품 p
where o.주문일시 >= add_months(sysdate, -1)
  and o.할인유형코드 = 'K890'
  and p.상품코드 = o.상품코드
group by p.상품코드
order by 총주문금액 desc, 상품코드
```

### 기존 쿼리 실행계획 설명
```
	1. 주문상품 테이블이 인덱스 주문상품_x1을 이용하여 스캔함. (cost=3k)
	2. 상품 테이블은 상품_pk로 unique 인덱스 스캔함
	3. 주문상품 테이블과 상품 테이블은 nl조인을 실행함.(cost=500K)
	4. 상품 테이블에서 상품코드별로 그룹핑이 일어남.
	5. 정렬이 일어남.
```

### 기존 실행 계획에 대한 나의 생각
이 실행계획은 nl조인했으며 드라이빙 테이블은 주문상품 테이블이다. `2만 개 상품을 고르게 주문` 한다는 말은 한 달별 주문상품 데이터 ndv가 2만개이다. 상품 데이터도 2만개인데 nl조인을 하기에 데이터가 많다. 이런 경우 해시조인을 적용하는 것이 좋을 것 같다. 그리고 주문상품 데이터가 총 1억 2천만 건이므로 인라인 뷰로 분리해서  데이터를 축소하는 것이 좋을 듯 하다. 

~~주문상품 데이터를 더 보자면 한 달치의 데이터 100만 건에서 `할인유형코드 K890` 만족하는 데이터는 20만 건이다. 선택도는 ( 20 / 100 = 20% ) 20%이므로 fts 가 더 나을 수 있다.~~
주문상품 테이블은 비파티션이므로 fts로 가면 1억 2천만 건의 데이터를 모두 읽어야 한다. 그러므로 인덱스를 타게 하여 20만 건의 데이터만 읽도록 수정해야 한다. 20만 건의 데이터만 읽게 되면 선택도는 (20 / 100 = 20%) 20% 이다. 그런데 문제에서 인덱스를 보면 `고객번호+상품코드+주문일시` , `주문일시+할인유형코드` 가 있는데 이는 효과적이지 못하다. 주문일시는 부등호 조건이기 때문에 나머지 할인유형코드가 필터 처리되기 때문이다. ~~따라서 `주문상품_x2(상품코드+할인유형코드+주문일시)` 인덱스를 새로 생성하여 인덱스를 타게 수정해야 한다.~~
따라서 `주문상품_x2(할인유형코드+주문일시+상품코드)` 인덱스를 새로 생성하여야 한다.

상품 테이블은 2만개이므로 full 스캔이 나을 듯 하다.

둘 중 누가 build input 테이블이 되느냐를 보면, 그래도 건수가 적은 상품 테이블이 build 테이블이 되는 것이 좋아보인다.

### 개선 튜닝
```
select /*+ leading(p o) use_hash(p) full(p) */
	p.상품코드, p.상품명, p.상품가격, 총주문수량
	, 총주문금액
from 상품 p, (
	select /*+ no_merge index(a 주문상품_x2) */ 
		상품코드, sum(주문수량) 총주문수량, sum(주문금액) 총주문금액
	from 주문상품 a
	where a.주문일시 >= add_months(sysdate, -1)
	  and a.할인유형코드 = 'K890'	
	  group by a.상품코드
) o
where p.상품코드 = o.상품코드
order by 총주문금액 desc, 상품코드

```

### 보완할 점
1. 인라인 뷰에 no_merge 힌트때문에 외부 상품 테이블과 독립적으로 먼저 처리된다. 따라서 인라인 뷰 블록에서 검색조건에는 `상품코드` 조건은 빠져있다. 새로운 인덱스를 `상품코드+할인유형코드+주문일시` 로 생성한다면 상품코드 컬럼이 없어서 인덱스 시작점과 종료점을 좁히지 못한다. 그러면 1억 2천만 건의 처음부터 필터를 거치게 된다.
```
주문상품_x2 (할인유형코드+주문일시+상품코드)	
```
