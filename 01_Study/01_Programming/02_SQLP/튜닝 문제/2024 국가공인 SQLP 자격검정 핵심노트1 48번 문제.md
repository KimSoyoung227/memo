### 테이블 구성 및 데이터
- 주문상품은 월 단위 파티션 테이블 (주문일시 기준)
- 한 달 주문상품 = 100만 건
- 주문상품의 보관 기간 = 10년
- 주문상품 총 건수 = 총 1억 2천만 건(=100만 * 120개월)
- 할인유형코드 조건을 만족하는 데이터 비중 = 20%
- 등록된 상품 = 2만 개
- 대부분 상품을 한 달에 한 개 이상 주문

### 인덱스 구성
- 상품_pk : 상품코드
- 주문상품_pk : 고객번호 + 상품코드 + 주문일시
- 주문상품_x1 : 주문일시 + 할인유형코드

### 튜닝 전 코드
```
select p.상품코드, min(p.상품명) 상품명, min(p.상품가격) 상품가격, sum(o.주문수량) 총주문수량
	, sum(o.주문금액) 총주문금액
from 주문상품 o, 상품 p
where o.주문일시 >= add_months(sysdate, -1)
  and o.할인유형코드 = 'K890'
  and p.상품코드 = o.상품코드
group by p.상품코드
order by 총주문금액 desc, 상품코드
```

### 기존 쿼리 실행계획 설명
```
	1. 주문상품 테이블이 파티션 프루닝이 적용되고 인덱스 주문상품_x1을 이용하여 스캔함. (cost=70k)
	2. 상품 테이블은 상품_pk로 unique 인덱스 스캔함
	3. 주문상품 테이블과 상품 테이블은 nl조인을 실행함.(cost=277)
	4. 상품 테이블에서 상품코드별로 그룹핑이 일어남.
	5. 정렬이 일어남.
```

### 기존 실행 계획에 대한 나의 생각1
이 실행계획은 nl조인했으며 드라이빙 테이블은 주문상품 테이블이다. `대부분 상품을 한 달에 한 개 이상 주문` 한다는 말은 한 달별 주문상품 데이터가 2만개 이상이다. 상품 데이터도 2만개인데 nl조인을 하기에 데이터가 많다. 이런 경우 해시조인을 적용하는 것이 좋을 것 같다.

주문상품 데이터를 더 보자면 월 파티션으로 관리되므로 한 달치의 데이터 100만 건에서 `할인유형코드 K890` 만족하는 데이터는 20만 건이다. 그 중에서 한 달치만 보면 최소 2만개니까, 선택도는 ( 20000 / 200000 = 0.1% ) 10%이므로 파티션 프루닝을 적용했어도 fts 가 더 나을 수 있다.

상품 테이블은 full 스캔이 나을 듯 하다.

### 개선 튜닝1
```
select /*+ leading(o p) use_hash(p) full(p) */
	p.상품코드, p.상품명, p.상품가격, 총주문수량
	, 총주문금액
from 상품 p, (
	select /*+ no_merge full(a) */ 
		상품코드, sum(주문수량) 총주문수량, sum(주문금액) 총주문금액
	from 주문상품 a
	where a.주문일시 >= add_months(sysdate, -1)
	  and a.할인유형코드 = 'K890'	
	  group by a.상품코드
) o
where p.상품코드 = o.상품코드
order by 총주문금액 desc, 상품코드

```

### 보완할 점1
1. `대부분 상품을 한 달에 한 개 이상 주문` 은 상품이 총 2만 개이므로, 한 달간 주문된 서로 다른 상품코드가 2만 개에 가까울 수 있다는 의미이다. 다만 이것은 전체 주문에 관한 설명이지, 반드시 `할인유형코드 K890` 인 상품도 2만 개라는 뜻은 아니다. 최근 한 달 전체 주문에는 대부분의 상품이 포함되지만, 그중 K890 주문에 포함된 서로 다른 상품 수는 문제에서 직접 제시하지 않았다. 따라서 주문상품 선택도는 'K890 주문상품 로우 수 / 대상 기간 전체 주문상품 로우 수' 로 계산해야 한다.

    > 20 / 100 = 20%
    
	따라서 주문상품에 대한 조건 선택도는 20%이다. 그러므로 주문상품 full 스캔 선택은 타당하다.
	
	인덱스 스캔을 계획할 경우 주문일시는 인덱스로 스캔하고, `할인유형코드`는 필터로 처리한다. 그렇게 되면 TABLE ACCESS BY ROWID로 처리되므로 랜덤 엑세스가 많이 발생한다.
