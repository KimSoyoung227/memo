### 테이블 구성 및 데이터
- 주문상품은 월 단위 파티션 테이블 (주문일시 기준)
- 한 달 주문상품 = 100만 건
- 주문상품의 보관 기간 = 10년
- 주문상품 총 건수 = 총 1억 2천만 건(=100만 * 120개월)
- 할인유형코드 조건을 만족하는 데이터 비중 = 20%
- 등록된 상품 = 2만 개
- 대부분 상품을 한 달에 한 개 이상 주문

### 인덱스 구성
- 상품_pk : 상품코드
- 주문상품_pk : 고객번호 + 상품코드 + 주문일시
- 주문상품_x1 : 주문일시 + 할인유형코드

### 튜닝 전 코드
```
select 상품코드, 상품명, 상품가격, 총주문수량, 총주문금액
from ( 
	select p.상품코드, min(p.상품명) 상품명, min(p.상품가격) 상품가격,
		 sum(o.주문수량) 총주문수량, sum(o.주문금액) 총주문금액
	from 주문상품 o, 상품 p
	where o.주문일시 >= add_months(sysdate, -1)
	  and o.할인유형코드 = 'K890'
	  and p.상품코드 = o.상품코드
	group by p.상품코드
	order by 총주문금액 desc, 상품코드
)
where rownum <= 100
```

### 기존 쿼리 실행계획 설명
```
	1. 주문상품 테이블이 파티션 프루닝이 적용되고 인덱스 주문상품_x1을 이용하여 스캔함. (cost=104k)
	2. 상품 테이블은 상품_pk로 unique 인덱스 스캔함
	3. 주문상품 테이블과 상품 테이블은 nl조인을 실행함.(cost=204k)
	4. 상품 테이블에서 상품코드별로 그룹핑이 일어남.
	5. 정렬이 일어남.
	6. stopkey 가 발생함
```

### 기존 실행 계획에 대한 나의 생각
일단 주문상품 테이블과 상품 테이블을 nl 조인하였다. nl조인을 하기에는 소량 데이터가 아니다. 

주문상품 테이블의 경우 1억 2천만 건에 대해서 파티션 프루닝으로 100만건으로 줄고, K890 조건을 만족해서 20만건으로 줄었다. `대부분 상품을 한 달에 한 개 이상 주문` 한다고 하는 조건은 데이터를 축소시켜주는 조건은 아니고 ndv가 2만개라는 말이다. 
일단 주문상품의 선택도를 계산해보면 (20 / 100 = 20%) 20%로 계산된다. 파티션 프루닝+fts가 더 나을 수 있다. 

상품 테이블의 경우 2만 건이기에 이 또한 full 스캔이 낫다.

두 테이블 중 build input을 정해야 하는데, 주문상품을 인라인뷰로 데이터 축소를 해놓은 상황이라면 어느 테이블이 build input이 되든 상관이 없다.
그러므로 일단 주문상품을 인라인 뷰로 변환하는 작업이 필요하다.

또 고려해야 하는 부분은 rownum <= 100인데, 이것은 부분범위처리이기 때문에 inner 뷰에서 미리 정렬을 완료해야한다. 또 rownum이 있으면 인라인 뷰를 내부적으로 merging하지 않는 것으로 알고 있으므로 no_merge 힌트를 제외해도 될 것 같다.

여기까지 오면 메인 안에 상품테이블 조인 쿼리 블럭, 그리고 그 안에 주문상품 쿼리 블럭까지 3개의 블럭을 만들 필요가 있는지 의심이 된다. 메인에 상품테이블을 빼는 것은 성능에 큰 차이가 없어보인다.

### 개선 튜닝1
```
select /*+ leading(o p) use_hash(p) full(p) */
	p.상품코드, p.상품명, p.상품가격, 총주문수량
	, 총주문금액
from (
	select /*+ full(a) */ 
		상품코드, sum(주문수량) 총주문수량, sum(주문금액) 총주문금액
	from 주문상품 a
	where a.주문일시 >= add_months(sysdate, -1)
	  and a.할인유형코드 = 'K890'	
	group by a.상품코드
	order by 총주문금액 desc, 상품코드
) o, 상품 p
where 1=1
and p.상품코드 = o.상품코드
and rownum <= 100
```

### 보완할 점1
1. 한 달 주문상품 100만 건 중 `할인유형코드=K890`을 만족하는 데이터는 20만 건이다. 2만 개 상품을 한 달에 한 개 이상 주문하므로 group by 결과 집합은 2만여 건이다. **상품코드당 주문상품은 평균 10건**이므로 group by 후 조인하면 조인 횟수를 (20만 / 2만 )**1/10로 줄일 수 있다.**
2. 등록된 2만 개 상품 중 100개만 조인하므로 해시 조인보다 nl 조인이 효과적이다.
3. 인라인 뷰에서  정렬한 결과집합 중 100건을 추출했는데 nl 조인 과정에서 배치I/O가 작동하면 출력 순서가 흐트러질 수 있으므로 정렬 기준을 바깥에 한 번 더 명시해야 한다.

### 최종 개선 쿼리
```
select /*+ leading(o p) use_nl(p) */
	p.상품코드, p.상품명, p.상품가격, 총주문수량
	, 총주문금액
from (
	select /*+ full(a) no_merge */ 
		상품코드, sum(주문수량) 총주문수량, sum(주문금액) 총주문금액
	from 주문상품 a
	where a.주문일시 >= add_months(sysdate, -1)
	  and a.할인유형코드 = 'K890'	
	group by a.상품코드
	order by 총주문금액 desc, 상품코드
) o, 상품 p
where 1=1
and p.상품코드 = o.상품코드
and rownum <= 100
order by 총주문금액 desc, 상품코드;

```

> Q1. '최종 개선 쿼리'에서 메인쿼리의 조건 순서가 어떻게 되는거야? 만약에 조인보다 rownum이 먼저 실행되면 어떻게 해?
> 
> A1. `ROWNUM`은 해당 쿼리 블록이 만들어 내는 결과 행에 번호를 붙인다는 점이다. 
> ```
> o의 한 행 -> p와 조인 조건 확인 -> 조인에 성공한 결과 행 생성 -> 그 결과 행에 ROWNUM 부여 -> 100건이 되면 중단
> ```
> 즉, ROWNUM은 조인 전의 o 행에 무조건 먼저 붙는 게 아니라, 조인 결과로 반환 가능한 행에 붙는 것으로 이해해야 한다.
> 
> 따라서 메인 블록의 흐름 순서는 아래와 같다.
> ```
> 1. 인라인 뷰 o에서 첫 번째 상품코드 읽기
> 2. 상품_pk로 p 조회
> 3. 조인 성공
> 4. 결과 행에 ROWNUM =1
> 5. 다음 o 행 처리
> 6. 100건이 되면 중단
> ```
